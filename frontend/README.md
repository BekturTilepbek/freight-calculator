## О проекте

**FreightFlow** — веб-приложение класса TMS (Transportation Management System) для управления грузоперевозками. Система автоматизирует ключевой бизнес-процесс диспетчерского отдела: расчет стоимости рейса, ведение заявок, назначение водителей, учет расходов и прибыли, бизнес-аналитика.

### Решаемая проблема

В типичной логистической компании диспетчер ежедневно проводит десятки расчетов: договаривается с брокером о ставке за милю, прикидывает расход топлива по дороге, оценивает маржу, сохраняет данные в Excel или Google Sheets. Этот процесс не автоматизирован, плохо поддается аудиту, легко содержит ошибки в формулах, и не дает единой картины бизнеса. Дополнительно — между диспетчером и водителем нет прозрачного цифрового канала: рейсы передаются в чатах или по телефону.

FreightFlow решает эти проблемы: предоставляет интерфейс для быстрого расчета с автоматическим определением расстояния по адресам, сохраняет полную историю расчетов и заявок в реляционной БД, разграничивает права доступа (администратор / диспетчер / водитель), и дает аналитику по всем рейсам.

### Целевая аудитория

- **Малые и средние логистические компании** в США (модель работы «диспетчер — брокер»), где FreightFlow заменяет таблицы и записные книжки.
- **Учебный материал** для демонстрации полного цикла современной веб-разработки: фронт, бэк, БД, контейнеризация, безопасность, миграции, интеграции с внешними API, тестирование.

```
                         │ HTTP / JSON (REST API)

┌─────────────────────────────────────────────────────────────┐
│  УРОВЕНЬ БИЗНЕС-ЛОГИКИ (Application Layer)                 │
│  FastAPI Backend                                           │
│  • API Routes — обработка HTTP-запросов                    │
│  • Services — бизнес-логика (калькулятор, маршрутизация)   │
│  • CRUD — операции с БД                                    │
│  • Schemas — валидация (Pydantic)                          │
│  • Security — JWT, bcrypt, RBAC                            │
└──────┬──────────────────────────┬───────────────────────────┘
       │ asyncpg                  │ httpx
       ▼                          ▼
┌────────────────────┐  ┌──────────────────────────────────────┐
│  PostgreSQL 16     │  │  ВНЕШНИЕ СЕРВИСЫ                     │
│  • 7 таблиц        │  │  • Nominatim (геокодинг)             │
│  • Миграции        │  │  • OSRM (построение маршрутов)       │
│  • JSONB поля      │  │  • OpenStreetMap (тайлы карт)        │
└────────────────────┘  └──────────────────────────────────────┘
```

### Контейнеризация

Каждый уровень — отдельный Docker-контейнер. Это обеспечивает:
- **Изоляцию зависимостей** — фронт и бэк не «сталкиваются» друг с другом версиями
- **Воспроизводимость** — проект разворачивается одной командой `docker compose up`
- **Простоту деплоя** — на production-сервере используются те же образы

### Асинхронная обработка

Backend полностью асинхронный: FastAPI + async SQLAlchemy + asyncpg + httpx. Один процесс может обрабатывать сотни одновременных соединений без блокировки, что критично для систем с интенсивным IO (запросы к БД, внешние геосервисы).

### Разделение ответственности

Структура бэкенда строго следует принципу разделения слоев:

- `models/` — определения таблиц БД (ORM)
- `schemas/` — валидация и сериализация (Pydantic)
- `crud/` — операции с БД
- `services/` — бизнес-логика (калькулятор стоимости, маршрутизация)
- `api/routes/` — HTTP-эндпоинты
- `core/` — конфигурация, безопасность

## Модель данных

### Таблицы

| Таблица | Назначение |
|---------|-----------|
| `users` | Пользователи системы (3 роли) |
| `clients` | Клиенты-грузовладельцы |
| `brokers` | Брокеры-посредники |
| `vehicles` | Транспортные средства |
| `orders` | Заявки на перевозку (центральная таблица) |
| `calculations` | История расчетов |

### Реляционные связи

```
users ──────┬─── orders (один диспетчер → много заявок)
            └─── vehicles (один водитель ↔ одно ТС)

clients ─────── orders (один клиент → много заявок)
brokers ─────── orders (один брокер → много заявок)
vehicles ────── orders (одно ТС → много заявок)

orders ──────── calculations (одна заявка → много расчетов)
```

### Ключевые поля таблицы `orders`

| Поле | Тип | Описание |
|------|-----|----------|
| id | INT | Первичный ключ |
| order_number | VARCHAR(50) | Бизнес-номер заявки |
| dispatcher_id | INT FK → users | Диспетчер-автор |
| vehicle_id | INT FK → vehicles | Назначенное ТС |
| client_id, broker_id | INT FK | Контрагенты |
| origin_address, destination_address | VARCHAR | Адреса |
| distance_miles, rate_per_mile | NUMERIC | Километраж, ставка |
| cargo_type, weight_lbs | | Информация о грузе |
| pickup_date, delivery_date | DATE | Плановые даты |
| status | ENUM | draft / assigned / in_transit / delivered / cancelled |

### Ключевые поля таблицы `calculations`

| Поле | Тип | Описание |
|------|-----|----------|
| id | INT | Первичный ключ |
| order_id | INT FK → orders | К какой заявке относится |
| distance_miles, rate_per_mile | NUMERIC | Входные параметры |
| fuel_consumption_mpg, fuel_price_per_gallon | NUMERIC | Параметры топлива |
| gross_revenue, fuel_cost | NUMERIC | Финансовые результаты |
| net_profit, margin_percent | NUMERIC | Прибыль и маржа |
| breakdown | JSONB | Детализация по статьям |
| created_at | TIMESTAMP | Момент расчета |

### Почему расчеты вынесены в отдельную таблицу

Историчность данных. Цена топлива меняется ежедневно, ставки за милю пересматриваются. Если пересчитать заявку через месяц с новыми параметрами — результат будет другим. Поэтому каждый расчет фиксируется как **исторический документ**: входные параметры на момент расчета сохраняются вместе с результатом.

### Миграции

Схема БД управляется через **Alembic** — стандарт де-факто для миграций в Python. Каждое изменение схемы создает отдельный файл миграции в `backend/alembic/versions/`, который можно применить (`upgrade`) или откатить (`downgrade`). Это аналог git для базы данных.

## Роли пользователей и права доступа

В системе реализована **ролевая модель доступа (RBAC — Role-Based Access Control)**. Три роли:

### Администратор (`admin`)
- Полный доступ ко всем функциям системы
- Управление пользователями
- Удаление любых сущностей (заявок, клиентов, брокеров, ТС)
- Просмотр аналитики

### Диспетчер (`dispatcher`) — основной пользователь
- Создание и ведение заявок
- Расчет стоимости рейсов
- Управление клиентами, брокерами, ТС
- Назначение водителей на рейсы (через назначение ТС)
- Просмотр дашборда и аналитики

### Водитель (`driver`)
- Видит **только свои** рейсы (привязанные через ТС)
- Смена статусов своих рейсов (Назначен → В пути → Доставлено)
- Простой мобильный интерфейс
- НЕ имеет доступа к дашборду, CRUD-страницам, аналитике

### Техническая реализация

На уровне backend используются две зависимости FastAPI:

```python
get_current_user           # извлекает пользователя из JWT-токена
require_role(*allowed)     # фабрика — пропускает только указанные роли
```

Пример защиты эндпоинта:
```python
@router.delete("/{order_id}")
async def delete_order(
    current_user: User = Depends(require_role(UserRole.ADMIN))
):
    ...
```

На уровне frontend используются **Navigation Guards** Vue Router и условные пункты меню. После логина водитель перенаправляется на свою отдельную страницу `/app/my-rides`, а не на общий дашборд.

## Основные функции

### 1. Калькулятор с автодистанцией

Диспетчер вводит **адреса** (откуда/куда) — система через Nominatim геокодирует их, через OSRM строит маршрут, автоматически подставляет расстояние и показывает время в пути. Дальше задается ставка за милю, расход топлива, цена топлива — мгновенно считается выручка, расходы, прибыль и маржа.

### 2. Управление заявками

- Список с фильтрами по статусу, поиском по адресам и номеру, пагинацией
- Карточка заявки с маршрутом, финансами, историей расчетов
- Смена статусов: Черновик → Назначен → В пути → Доставлено
- Назначение ТС → автоматический переход в статус «Назначен»
- Карта маршрута по запросу
- Экспорт списка заявок в Excel

### 3. CRUD справочников

- Клиенты — название, контактное лицо, email, телефон
- Брокеры — название, MC Number (Motor Carrier — реквизит из США), контакты
- Транспортные средства — гос. номер, марка, модель, расход топлива, привязка к водителю

### 4. Дашборд с аналитикой

- 4 KPI-карточки: активные рейсы, всего заявок, общая выручка, общий пробег
- Линейный график выручки по месяцам
- Donut-диаграмма распределения статусов
- Топ-5 маршрутов (горизонтальные бары)
- Таблица последних заявок

### 5. Кабинет водителя

Отдельная страница с упрощенным интерфейсом:
- Сводка: количество активных рейсов
- Карточки активных рейсов с маршрутом и финансами
- Кнопки «Начать рейс» / «Завершить рейс» — смена статуса
- Список завершенных рейсов

### 6. Авторизация и регистрация

- JWT-аутентификация (токены на 24 часа)
- Bcrypt-хеширование паролей
- Защита всех приватных страниц через Navigation Guards
- Светлая и темная тема интерфейса
- Демо-кнопки быстрого входа для проверки

## Полный TMS-цикл

Сквозной сценарий, который проходит через все роли:

```
1. ДИСПЕТЧЕР: Калькулятор
   ├── Вводит адреса → автодистанция
   ├── Вводит ставку, параметры топлива → расчет прибыли
   └── Сохранить как заявку (+ клиент, брокер, груз, даты)
   
2. ДИСПЕТЧЕР: Карточка заявки (статус: Черновик)
   └── Назначает ТС из списка
       └── Статус автоматически → Назначен
   
3. ВОДИТЕЛЬ: Логинится → видит рейс в "Мои рейсы"
   ├── Нажимает "Начать рейс" → статус: В пути
   └── Нажимает "Завершить рейс" → статус: Доставлено
   
4. ДИСПЕТЧЕР: Дашборд
   ├── Видит обновленную аналитику
   ├── Заявка перешла в статистику "выручки"
   └── Может экспортировать отчет в Excel
```

## Алгоритм расчета стоимости

Реализован в `backend/app/services/cost_calculator.py` с использованием паттерна «компоненты стоимости» — каждая статья расхода считается отдельно и складывается в общий результат. Это позволяет легко добавлять новые статьи (платные дороги, простой, страховка) без переписывания ядра.

### Формула

```
1. Выручка:
   gross_revenue = distance_miles × rate_per_mile

2. Расход топлива в галлонах:
   gallons = distance_miles / fuel_consumption_mpg

3. Стоимость топлива:
   fuel_cost = gallons × fuel_price_per_gallon

4. Дополнительные расходы (платные дороги, погрузка):
   extra_costs_total = Σ(extra_cost_items)

5. Итоговые расходы:
   total_expenses = fuel_cost + extra_costs_total

6. Чистая прибыль:
   net_profit = gross_revenue - total_expenses

7. Маржа (%):
   margin_percent = (net_profit / gross_revenue) × 100
```

### Точность вычислений

Все денежные значения хранятся и обрабатываются как **`Decimal`** — специальный тип Python для точной арифметики. Использование `float` для денег недопустимо из-за ошибок округления (классическая проблема: `0.1 + 0.2 ≠ 0.3` в IEEE 754). `Decimal` исключает эту ошибку, что критично для финансовых расчетов и подтверждается тестами.

## Интеграция с картографическими сервисами

### Стек

| Сервис | Функция | Преимущества |
|--------|---------|--------------|
| **Nominatim** | Геокодирование адресов → координаты | Открытый, бесплатный, без API-ключа |
| **OSRM** | Построение маршрута между координатами | Открытый, точный, возвращает GeoJSON |
| **OpenStreetMap** | Тайлы карты | Открытые данные сообщества |
| **Leaflet** | Рендеринг карт в браузере | Легкий, без зависимости от Google Maps |

### Пайплайн

```
Адрес "Chicago, IL"
       ↓ Nominatim
Координаты (41.85, -87.65)
       ↓ + координаты пункта назначения
OSRM
       ↓
{ distance_meters, duration_seconds, geometry: GeoJSON LineString }
       ↓
distance_miles = 925.14, отрисовка маршрута на Leaflet
```

### Преимущества выбранного решения

- **Полностью бесплатно** — никаких API-ключей или подписок
- **Open source** — в production можно поднять собственные инстансы Nominatim и OSRM, устраняя зависимость от публичных сервисов и rate limits
- **Соответствует open data философии** — данные OpenStreetMap собираются сообществом

- Защита эндпоинтов без токена
- Защита от невалидного токена
- Получение информации о текущем пользователе

**CRUD заявок:**
- Создание заявки
- Получение списка
- Получение по ID
- Обработка несуществующего ID
- Обновление статуса
- Корректность расчета через API

**Ролевая модель:**
- Админ может удалить заявку
- Диспетчер не может удалить заявку (403)
- Водитель имеет доступ к своему эндпоинту
- Диспетчер не имеет доступа к эндпоинту водителя

### Изоляция тестов

Каждый тест получает **чистую БД** в памяти (in-memory SQLite) через систему фикстур pytest. Подключение к продакшен-БД во время тестов исключено благодаря механизму `dependency_overrides` в FastAPI.

### Запуск

```bash
docker compose exec backend pytest
docker compose exec backend pytest --cov=app --cov-report=term-missing  # с покрытием
```

**Покрытие кода:** ~85% (включая 100% покрытие моделей, схем, калькулятора стоимости).

## Обоснование технических решений

### Почему FastAPI

- **Производительность.** Среди всех Python-фреймворков один из самых быстрых благодаря асинхронной модели на Starlette.
- **Автоматическая документация API.** Из type hints и Pydantic-схем генерируется интерактивный Swagger UI без единой строки документационного кода.
- **Type Safety.** Использование типов Python и Pydantic минимизирует баги на этапе разработки.
- **Современность.** Активная разработка, использование в production такими компаниями как Netflix, Uber, Microsoft.

### Почему Vue 3

- **Низкий порог входа.** Vue 3 проще освоить с нуля, чем React или Angular.
- **Composition API.** Современный API для переиспользуемой логики.
- **Меньше boilerplate** по сравнению с React.

### Почему PostgreSQL

- **ACID-гарантии.** Транзакции обеспечивают целостность финансовых данных.
- **JSONB.** Используется для хранения детализации расчетов — гибрид реляционной и документной БД.
- **Зрелость и стабильность.** PostgreSQL развивается с 1996 года.
- **Расширяемость.** Поддержка PostGIS (геопоиск), полнотекстового поиска — задел для будущих фич.

### Почему async SQLAlchemy

- **Соответствие async-стилю FastAPI.** Синхронный ORM в асинхронном фреймворке создает блокировки event loop'а.
- **Высокая производительность** под нагрузкой.

### Почему Alembic

- **Версионирование схемы БД** — каждое изменение фиксируется в виде кода.
- **Автогенерация миграций** на основе сравнения моделей и состояния БД.
- **Стандарт экосистемы** SQLAlchemy.

### Почему JWT

- **Stateless-авторизация** — упрощает горизонтальное масштабирование.
- **Стандарт RFC 7519**, реализован во всех языках и фреймворках.
- **Простая интеграция с SPA** через interceptor.

### Почему bcrypt

- **Адаптивная сложность** защищает от brute-force.
- **Встроенная соль** делает невозможным использование радужных таблиц.
- **Рекомендован OWASP** для хеширования паролей.

### Почему Nominatim + OSRM (а не Google Maps)

- **Бесплатно и без API-ключей** — упрощает развертывание.
- **Open Source** — в production можно поднять собственные инстансы.
- **Качественные данные OpenStreetMap** — точность для логистических задач достаточная.

### Почему Docker и Docker Compose

- **Воспроизводимость** на любой машине с Docker.
- **Изоляция зависимостей** — версии Python, Node, PostgreSQL фиксированы.
- **Простота деплоя** — те же образы используются в dev и prod.

## Безопасность

### Хеширование паролей
Пароли никогда не хранятся в открытом виде. Bcrypt с автоматической генерацией соли. Лимит длины в 72 байта обрабатывается явно (требование bcrypt).

### JWT-токены
Подписываются HS256 секретным ключом, в production хранится в переменных окружения с длиной не менее 32 случайных символов. Срок жизни — 24 часа.

### Защита от SQL-инъекций
Все запросы к БД через ORM SQLAlchemy с параметризованными запросами. Прямые конкатенации SQL отсутствуют.

### Валидация входных данных
Pydantic-схемы проверяют:
- Типы данных
- Обязательность полей
- Диапазоны (gt=0 для денег)
- Корректность email через RFC 5322

### Ролевая модель доступа (RBAC)
Каждый эндпоинт явно указывает разрешенные роли. Попытка несанкционированного вызова → HTTP 403.

### Принцип наименьших привилегий
Новые пользователи получают роль `dispatcher`. Роль `admin` назначается только вручную через БД.

### Защита от brute-force при логине
Унифицированный ответ 401 на «пользователь не найден» и «неверный пароль» — атакующий не может узнать, существует ли email в системе.

### CORS
Настроен CORS Middleware. В production ограничивается конкретным доменом фронтенда.
