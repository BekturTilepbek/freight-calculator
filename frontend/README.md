## О проекте

**FreightFlow** — веб-приложение класса TMS (Transportation Management System) для управления грузоперевозками. Система автоматизирует ключевой бизнес-процесс диспетчерского отдела: расчет стоимости рейса, ведение заявок, учет расходов и прибыли.

### Решаемая проблема

В типичной логистической компании диспетчер ежедневно проводит десятки расчетов: договаривается с брокером о ставке за милю, прикидывает расход топлива по дороге, оценивает маржу, сохраняет данные в Excel или Google Sheets. Этот процесс не автоматизирован, плохо поддается аудиту, легко содержит ошибки в формулах, и не дает единой картины бизнеса.

FreightFlow решает эту проблему: предоставляет интерфейс для быстрого расчета, сохраняет полную историю расчетов и заявок в реляционной БД, разграничивает права доступа (администратор / диспетчер / водитель), и дает аналитику по всем рейсам.

### Целевая аудитория

- **Малые и средние логистические компании** в США (модель работы «диспетчер — брокер»), где FreightFlow заменяет таблицы и записные книжки.
- **Учебный материал** для демонстрации полного цикла современной веб-разработки: фронт, бэк, БД, контейнеризация, безопасность, миграции.

## Архитектура приложения

FreightFlow построен по классической **трехуровневой архитектуре** (three-tier architecture):

```
┌─────────────────────────────────────────────────────────────┐
│  УРОВЕНЬ ПРЕДСТАВЛЕНИЯ (Presentation Layer)                │
│  Vue 3 SPA — браузер пользователя                          │
│  • Lending, Login, Register                                │
│  • Dashboard, Orders, OrderDetail, Calculator              │
└────────────────────────┬────────────────────────────────────┘
                         │ HTTP / JSON (REST API)
                         ▼
┌─────────────────────────────────────────────────────────────┐
│  УРОВЕНЬ БИЗНЕС-ЛОГИКИ (Application Layer)                 │
│  FastAPI Backend                                           │
│  • API Routes — обработка HTTP-запросов                    │
│  • Services — бизнес-логика (калькулятор)                  │
│  • CRUD — операции с БД                                    │
│  • Schemas — валидация (Pydantic)                          │
│  • Security — JWT, bcrypt, RBAC                            │
└────────────────────────┬────────────────────────────────────┘
                         │ asyncpg
                         ▼
┌─────────────────────────────────────────────────────────────┐
│  УРОВЕНЬ ДАННЫХ (Data Layer)                               │
│  PostgreSQL 16                                             │
│  • 6 таблиц с реляционными связями                         │
│  • Миграции через Alembic                                  │
└─────────────────────────────────────────────────────────────┘
```

### Все компоненты контейнеризованы

Каждый уровень — отдельный Docker-контейнер. Это обеспечивает:
- **Изоляцию зависимостей** — фронт и бэк не «сталкиваются» друг с другом версиями
- **Воспроизводимость** — проект разворачивается одной командой `docker compose up`
- **Простоту деплоя** — на production-сервере используются те же образы

### Асинхронная обработка запросов

Backend полностью асинхронный: FastAPI + async SQLAlchemy + asyncpg. Это позволяет одному процессу обрабатывать сотни одновременных соединений без блокировки, что критично для систем с интенсивным IO (запросы к БД, внешние API).

### Разделение ответственности (Separation of Concerns)

Структура бэкенда строго следует принципу разделения слоев:

- `models/` — определения таблиц БД (ORM)
- `schemas/` — валидация и сериализация данных (Pydantic)
- `crud/` — операции с БД
- `services/` — бизнес-логика (например, расчет стоимости)
- `api/routes/` — HTTP-эндпоинты
- `core/` — конфигурация, безопасность

Такая структура упрощает тестирование, поддержку и масштабирование.

### Реляционные связи

```
users ──────┬─── orders (один диспетчер → много заявок)
            └─── vehicles (один водитель → одно ТС)

clients ─────── orders (один клиент → много заявок)
brokers ─────── orders (один брокер → много заявок)
vehicles ────── orders (одно ТС → много заявок)

orders ──────── calculations (одна заявка → много расчетов)
```

### Почему расчеты вынесены в отдельную таблицу

Историчность данных. Цена топлива меняется ежедневно, ставки за милю пересматриваются. Если пересчитать заявку через месяц с новыми параметрами — результат будет другим. Поэтому каждый расчет фиксируется как **исторический документ**: входные параметры на момент расчета сохраняются вместе с результатом. Это позволяет:
- Восстановить, какой именно расчет лег в основу решения
- Видеть, как менялись параметры при пересмотре
- Использовать «снимок» данных для генерации документов

### Миграции

Схема БД управляется через **Alembic** — стандарт де-факто для миграций в Python-экосистеме. Каждое изменение схемы создает отдельный файл миграции в `backend/alembic/versions/`, который можно применить (`upgrade`) или откатить (`downgrade`). Это аналог git для базы данных.

## Роли пользователей и права доступа

В системе реализована **ролевая модель доступа (RBAC — Role-Based Access Control)**. Три роли:

### Администратор (`admin`)
- Полный доступ ко всем функциям системы
- Управление пользователями
- Удаление любых сущностей (заявок, клиентов, брокеров)
- Настройка системных параметров

### Диспетчер (`dispatcher`) — основной рабочий пользователь
- Просмотр и создание заявок
- Расчет стоимости рейсов
- Управление клиентами и брокерами
- Назначение водителей и ТС на рейсы
- Просмотр дашборда и аналитики

### Водитель (`driver`)
- Просмотр назначенных ему рейсов
- Смена статуса своих рейсов (в пути / доставлено)
- Просмотр деталей маршрута

### Техническая реализация

На уровне backend используются две зависимости FastAPI:

```python
get_current_user           # извлекает пользователя из JWT-токена
require_role(*allowed)     # фабрика — пропускает только указанные роли
```

Пример защиты эндпоинта:
```python
@router.delete("/{order_id}")
async def delete_order(
    current_user: User = Depends(require_role(UserRole.ADMIN))
):
    ...
```

На уровне frontend используются **Navigation Guards** Vue Router: при переходе на защищенный маршрут проверяется наличие токена в Pinia-сторе авторизации; при его отсутствии происходит редирект на страницу логина.

## Основные функции

### 1. Калькулятор стоимости

Главная фича системы. Диспетчер вводит:
- Расстояние в милях
- Ставку за милю (договоренность с брокером)
- Расход топлива (MPG)
- Цену топлива

Система мгновенно показывает:
- Выручку
- Стоимость топлива
- Чистую прибыль
- Маржу в процентах
- Детализацию по статьям расходов

Можно сохранить расчет как новую заявку — она появится в общем списке.

### 2. Управление заявками

- **Список заявок** с фильтрацией по статусу, поиском по номеру/адресам, пагинацией и сортировкой
- **Карточка заявки** — маршрут, груз, финансы, история всех расчетов по этой заявке
- **Смена статусов** — Черновик → Назначен → В пути → Доставлено
- **Опциональный экспорт** в PDF (планируется)

### 3. Дашборд

Сводная страница со статистикой:
- Активные рейсы
- Общая выручка
- Средняя маржа
- Общий пробег
- Таблица последних 5 заявок

### 4. Авторизация и регистрация

- JWT-аутентификация с токенами на 24 часа
- Bcrypt-хеширование паролей
- Защита всех приватных страниц через Navigation Guards
- Светлая и темная тема интерфейса

## Алгоритм расчета стоимости

Реализован в модуле `backend/app/services/cost_calculator.py` с использованием паттерна «компоненты стоимости» — каждая статья расхода считается отдельно и складывается в общий результат. Это позволяет легко добавлять новые статьи (платные дороги, простой, страховка) без переписывания ядра.

### Формула

```
1. Выручка (gross_revenue):
   gross_revenue = distance_miles × rate_per_mile

2. Расход топлива в галлонах:
   gallons = distance_miles / fuel_consumption_mpg

3. Стоимость топлива:
   fuel_cost = gallons × fuel_price_per_gallon

4. Дополнительные расходы (платные дороги, погрузка и т.д.):
   extra_costs_total = Σ(extra_cost_items)

5. Итоговые расходы:
   total_expenses = fuel_cost + extra_costs_total

6. Чистая прибыль:
   net_profit = gross_revenue - total_expenses

7. Маржа (%):
   margin_percent = (net_profit / gross_revenue) × 100
```

### Точность вычислений

Все денежные значения хранятся и обрабатываются как **`Decimal`** — специальный тип Python для точной арифметики с плавающей запятой. Использование `float` для денег недопустимо из-за ошибок округления (классическая проблема: `0.1 + 0.2 ≠ 0.3` в IEEE 754). `Decimal` исключает эту ошибку, что критично для финансовых расчетов.

## Быстрый старт

### Требования
- Docker Desktop (или Docker Engine + Compose)
- Свободные порты 5173, 8000, 5432

### Запуск

```bash
# 1. Клонировать репозиторий
git clone https://github.com/<username>/freight-calculator.git
cd freight-calculator

# 2. Создать .env из шаблона
cp .env.example .env

# 3. Запустить все сервисы
docker compose up -d --build

# 4. Применить миграции
docker compose exec backend alembic upgrade head

# 5. Заполнить тестовыми данными
docker compose exec backend python -m app.db.seed
```

### Доступ

- **Frontend:** http://localhost:5173
- **Backend API:** http://localhost:8000
- **Swagger UI:** http://localhost:8000/docs
- **PostgreSQL:** localhost:5432 (логин/пароль в `.env`)

## Команды для разработки

```bash
# Запуск/остановка
```

## Обоснование технических решений

### Почему FastAPI

- **Производительность.** Среди всех Python-фреймворков FastAPI один из самых быстрых благодаря асинхронной модели и базе на Starlette.
- **Автоматическая документация API.** Из type hints и Pydantic-схем генерируется интерактивный Swagger UI и OpenAPI-спецификация — без единой строки документационного кода.
- **Type Safety.** Использование типов Python и Pydantic минимизирует баги, связанные с неправильными данными на входе или выходе API.
- **Современность.** Активная разработка, большое сообщество, использование в production такими компаниями как Netflix, Uber, Microsoft.

### Почему Vue 3

- **Низкий порог входа.** Vue 3 проще освоить с нуля, чем React или Angular, при этом сопоставимый по возможностям.
- **Composition API.** Современный API позволяет писать переиспользуемую логику, аналогично React Hooks, но с более понятной семантикой.
- **Меньше boilerplate.** Меньше шаблонного кода по сравнению с React, что ускоряет разработку при ограниченных сроках.

### Почему PostgreSQL

- **ACID-гарантии.** Транзакции обеспечивают целостность финансовых данных, что критично для системы расчетов.
- **Поддержка JSONB.** Используется для хранения детализации расчетов (`breakdown`) — гибрид реляционной и документной БД.
- **Зрелость и стабильность.** PostgreSQL развивается с 1996 года, проверен на крупных проектах.
- **Расширяемость.** Поддержка PostGIS (геопоиск), полнотекстового поиска, материализованных представлений — все это можно использовать в будущих версиях системы.

### Почему async SQLAlchemy

- **Соответствие async-стилю FastAPI.** Использование синхронного ORM в асинхронном фреймворке создает блокировки event loop'а и убивает преимущества асинхронности.
- **Высокая производительность под нагрузкой.** Один процесс может обрабатывать сотни параллельных запросов к БД.

### Почему Alembic

- **Версионирование схемы БД.** Каждое изменение фиксируется в виде кода, который можно применить и откатить.
- **Автогенерация миграций.** На основе сравнения текущих ORM-моделей и состояния БД Alembic генерирует SQL автоматически.
- **Стандарт экосистемы.** Используется во всех серьезных проектах на SQLAlchemy.

### Почему JWT

- **Stateless-авторизация.** Backend не хранит сессии на сервере — вся информация о пользователе закодирована в самом токене. Это упрощает масштабирование (можно добавлять реплики бэкенда без общего хранилища сессий).
- **Стандарт.** RFC 7519, реализован во всех языках и фреймворках.
- **Простая интеграция с SPA.** Токен хранится на клиенте и автоматически добавляется к каждому запросу через interceptor.

### Почему bcrypt

- **Адаптивная сложность.** В отличие от MD5 или SHA-256, bcrypt намеренно медленный — это защищает от brute-force атак. Сложность можно увеличивать со временем при росте вычислительных мощностей атакующих.
- **Встроенная соль.** Каждый хеш содержит уникальную соль, что делает невозможным использование радужных таблиц.
- **Индустриальный стандарт.** Рекомендован OWASP для хеширования паролей.

### Почему Docker и Docker Compose

- **Воспроизводимость.** Проект разворачивается одной командой на любой машине с Docker.
- **Изоляция зависимостей.** Версии Python, Node, PostgreSQL фиксированы в Dockerfile — нет проблем «у меня работает, у тебя нет».
- **Простота деплоя.** Те же образы используются в development и production.
- **Микросервисный подход.** Frontend, backend, БД — отдельные сервисы, которые можно независимо масштабировать.

## Безопасность

В проекте реализованы следующие меры безопасности:

### Хеширование паролей
Пароли никогда не хранятся в открытом виде. Используется bcrypt с автоматической генерацией соли. Лимит длины пароля в 72 байта обрабатывается явно (требование bcrypt).

### JWT-токены
Подписываются алгоритмом HS256 секретным ключом, который в production должен храниться в переменных окружения и иметь длину не менее 32 случайных символов. Срок жизни — 24 часа.

### Защита от SQL-инъекций
Все запросы к БД выполняются через ORM SQLAlchemy с использованием параметризованных запросов. Прямые конкатенации SQL отсутствуют.

### Валидация входных данных
Все запросы к API проходят через Pydantic-схемы, которые проверяют:
- Типы данных
- Обязательность полей
- Диапазоны значений (например, `gt=0` для денег)
- Корректность email через валидатор RFC 5322

### Ролевая модель доступа (RBAC)
Каждый эндпоинт явно указывает, какие роли могут его вызывать. Попытка вызова без нужных прав возвращает HTTP 403.

### CORS
Настроен CORS Middleware для контроля cross-origin запросов. В production должен быть ограничен конкретным доменом фронтенда.

### Принцип наименьших привилегий
По умолчанию все новые пользователи получают роль `dispatcher` с минимально необходимыми правами. Роль `admin` назначается только вручную.
